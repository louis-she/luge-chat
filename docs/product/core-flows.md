# 路鸽 · 真机核心流程

> **文档性质**：产品说明 + 必要技术细节。改功能时同步改本文。  
> **范围**：真机默认路径（火山 RTC「打电话」）。`luge-chat` 仅服务主动讲解与黄点预览，不再提供 HTTP 问路（`mode=ask` 已下线）。  
> **更新**：2026-08-24（高德全面下线，地理数据改自建 PostGIS + OSM 底库；§6 重写；§7 改为「外部 API 调用一览：零」）

---

## 1. 产品在解决什么

路鸽是自驾场景的语音导游：用户开车时点开 App，像打电话一样和 AI 对话；系统也能在合适时机**主动开口**讲路边风景名胜。

真机上，语音的听/说/打断由**火山引擎 RTC + 智能体**完成；「车在哪、周边有什么、扣不扣次、记不记足迹」由路鸽自建后端（`api.luge.chat`）负责。

---

## 2. 总架构（真机）

```
┌─────────────────┐     RTC 音视频房间      ┌──────────────────────────┐
│  iOS / Android  │ ←──────────────────→ │ 火山：ASR + LLM + TTS    │
│  Expo App       │                      │ （可打断、全双工）         │
└────────┬────────┘                      └────────────┬─────────────┘
         │ 进房 Token / StartVoiceChat                │ 服务端回调
         │ 上报 GPS / 主动讲解 External TTS           │ Function Calling
         ▼                                            ▼
              ┌─────────────────────────────────────────┐
              │  api.luge.chat（Supabase Edge Functions） │
              │  · volc-voice-chat（进房、启停智能体）      │
              │  · volc-voice-callback（扣次、FC、足迹）    │
              │  · luge-chat（主动讲解判定 / 黄点预览）     │
              │  · PostGIS 地理库（地物 + 行政区）        │
              └─────────────────────────────────────────┘
```

| 层级 | 职责 |
|------|------|
| App | 进房/挂断、麦克风、GPS 上报、主动讲解触发与播报、配额展示 |
| 火山 | 实时语音识别、对话、TTS、用户打断 |
| 路鸽后端 | 配额、地理检索、足迹、主动讲解选点与文案 |

**密钥**：火山 RTC/OpenAPI、DeepSeek、天地图 `TIANDITU_KEY`（须为**服务端**类型）只在服务器；客户端不直连任何地图服务。

## 3. 会话生命周期

用户在雷达页点「路鸽」≈ 拨通电话；再点 ≈ 挂断。

| 步骤 | 谁做 | 说明 |
|------|------|------|
| 1. 校验额度 | App → `volc-voice-chat` | 用尽则不开通；提示购买 |
| 2. 发 RTC Token + 进房 | App + `volc-voice-chat` | 音频房间 |
| 3. `StartVoiceChat` | `volc-voice-chat` → 火山 | 挂上路鸽人设、欢迎语、FC 工具 |
| 4. 循环上报位置 | App | 供 FC「查周边」与足迹用当前坐标 |
| 5. 通话中问答 / 主动讲解 | 见下文两章 | |
| 6. 挂断 | App → 停智能体 + 退房 | 刷新剩余次数 |

通话过程中，火山通过 **RTS 回调** 打到 `volc-voice-callback`（如 `answerFinish`、字幕、Function Call）。

## 4. 问路（用户主动说话）

### 4.1 用户感知

用户问例如：「左边那条河叫什么？」「前面那座山是啥？」  
AI 口语回答，可随时打断。有登录时，一轮完整问答可能写入**足迹**。

### 4.2 流程

```
用户说话
  → 火山 ASR
  → 火山大模型组织回答
      │
      ├─ 需要地理信息时
      │     Function Call：get_nearby_landmarks
      │       → volc-voice-callback
      │       → PostGIS：点名问某地物就按名字搜，
      │         泛问取最近若干条
      │       → 结果回传给火山模型
      │
      └─ TTS 播给用户
  → 回调 answerFinish
      → 按 RoundID 去重，扣 1 次问路额度
  → 字幕/问答落库齐后
      → 尝试写入或匹配足迹（登录用户）
```

### 4.3 扣次规则（问路）

| 时机 | 行为 |
|------|------|
| 进房前 | 额度已用尽 → 不允许开始通话 |
| AI **说完一句**（`answerFinish`） | 扣 **1 次**；同一 `RoundID` 只扣一次 |
| 通话中途用尽 | 当前不自动挂断；下次进房会被拦 |

扣次身份：登录用户用账号额度；游客用设备维度额度（会话上绑定 `luge_user_id` / `device_key`）。

**为什么要 `RoundID` 去重：**  
扣次完全依赖火山服务端回调，不信 App 自报。同一轮 `answerFinish` 可能因网络重试、对方重复投递而被打多次；若不去重，一次问答会扣多次费。  
实现上表 `voice_chat_round_charges` 对 `(task_id, round_id)` 做唯一约束：同一通话任务里，每个 Round 只成功扣一次，重复回调直接忽略。  
产品约定仍是「AI 成功答完一轮再扣」；RoundID 去重是这条规则的防重复保险，不是给用户看的「问了几轮」计数。

### 4.4 地理怎么查（问路）

工具：`get_nearby_landmarks`（实现：`volc-voice-chat/nearbyLandmarks.ts`）。

1. 用客户端上报的最新经纬度（可带朝向）  
2. `resolve_geo_context` 拿场景（城/镇/野），**按「场景 × 语意」算出搜索半径**（见 §4.4.1；**不是**固定 3km）  
3. 用户点名问某个地物（「澜沧江还有多远」）→ `fuzzy_geo_landmarks` 在**整个半径内按名字搜**；名字对不上就用近音规则救援（ASR 常把首字听错）  
4. 泛问（「附近有什么」）→ `nearby_geo_landmarks` 取最近 8 条  
5. 结果整理成简短列表回给模型（含相对方向、距离；note 里带半径公式便于排障）

模型回答内容由火山侧生成；路鸽保证「周边事实」来自本地库，而不是模型瞎编坐标。  
**模型不再指定 `radius_m`**；`focus` 只作语意提示（「水库」「雪山」等）。泛化词（「湖」「水」）**不会**当作专名去精确匹配，避免把自己搜空。

> 各表分别干什么，见 **§6**。不要把「撞库」理解成「逆地理」。

#### 4.4.1 搜索半径怎么算（场景 × 语意）

上限 **100km**。原本是 50km（高德 API 的硬限制），下线高德后放宽，「前面二十公里那座雪山」才答得上。

**公式（有权重，可配）：**

```
radius_m = clamp( round( baseKm[scene] × mult[intent] × 1000 ) , 1000 , 50000 )
```

| 维 | 取值 | 默认权重 | 含义 |
|----|------|----------|------|
| **场景 scene** | `urban` / `town` / `wild` | 底径 **4 / 6 / 10** km | 由逆地理：街道门牌→城；镇乡→镇；镇乡+国道/高速/景区路→野 |
| **语意 intent** | `nearby` / `water` / `mountain` / `distant` / `landmark` | 倍率 **1 / 1.5 / 2.5 / 3 / 1.2** | 由工具 `focus` 关键词归类 |

**举例（默认权重）：**

| 场景 | 问法 | 计算 | 半径 |
|------|------|------|------|
| 野外 | 「旁边有水库吗」→ water | 10 × 1.5 | **15 km**（盖住紫坪铺挂名点 ~3km） |
| 野外 | 「前面那座雪山」→ mountain | 10 × 2.5 | **25 km** |
| 城市 | 「旁边有什么」→ nearby | 4 × 1 | **4 km** |

**可配置：**「我的 → 高级设置」里可改三档底径与五个倍率；通话中随 GPS 上报写入 `voice_chat_session_loc.geo_radius_prefs`，FC 回调读取。未上报时用上表默认。  
实现：`_shared/geoSearchRadius.ts`、客户端 `lib/geoRadiusPrefs.ts` / `lib/proactiveSettings.ts`。

> 主动讲解半径 = **场景底径**（与上表城/镇/野相同，不乘语意倍率）。预览黄点 / 风景库预热可用更大的固定 `scenicRadiusKm`，服务端会再按场景收窄。

### 4.5 足迹（问路相关）

- **不**在用户只听主动讲解时写足迹。  
- 用户**主动问完一轮**（问句 + 答句能对齐）后，后端尝试：匹配已有足迹或新建。  
- 若上一句刚播过主动讲解，且用户在追问同一 POI，可视为「延续深聊」，有利于归到同一足迹。

实现落在 `volc-voice-callback`（字幕 / `voice_chat_round_dialog` + 足迹逻辑）。路测验收仍以真机为准。

## 5. 主动讲解（系统主动开口）

### 5.1 用户感知

「我的」里打开**主动讲解**后，开车满足条件时，路鸽会自己讲附近**一处风景名胜**（短口播）。  
同一景点**当天不重复讲**（按上海日历日）。

主动讲解**每次发起检查都会扣 1 次**问路额度（即使最终决定不播，例如附近没有候选）。

### 5.2 何时启用

同时满足：

- 用户打开了主动讲解开关  
- 真机雷达上**路鸽通话已接通**（`inCall`）  
- 非「忙」状态（避免和进房握手等冲突）

### 5.3 触发门槛（客户端）

启动通话后先记一个**查询锚点**。之后 GPS 更新时检查：

| 条件 | 默认 | 含义 |
|------|------|------|
| 位移 | ≥ **20 km**（可在「我的 → 高级设置」改） | 相对上次查询锚点 |
| 查询间隔 | ≥ **10 min**（可配） | 距上次查询 |
| 开口间隔 | ≥ **15 min**（可配） | 距上次真正播报 |

位移与查询间隔必须**同时**满足才请求后端。路测可用高级设置里的「路测宽松 / 极松调试」预设，无需改环境变量或重编译。

实现：`lib/useProactiveGuide.ts` + `lib/proactiveSettings.ts` + `app/advanced-settings.tsx`。

### 5.4 后端选点与文案（`luge-chat` · `mode=proactive`）

```
门槛满足 → App 调 luge-chat（带当天已讲 POI 键 + 可选风景库缓存 + geo_radius_prefs）
  1. 扣 1 次额度
  2. `resolve_geo_context` → 行政区（喂 prompt）+ **判定场景**（城/镇/野）
  3. **搜索半径 = 场景底径**（默认城 4 / 镇 6 / 野 10 km；高级设置可改；**不乘**语意倍率）
  4. `nearby_geo_landmarks` 取 40 条候选，跳过村庄（或读客户端风景库后按场景半径过滤；圈内过少则补搜）
  5. 代码去重；每条候选带 **相对车头方位 + 距当前位置距离**（按当前 GPS 重算）
  6. 过滤「今天已讲过」
  7. 无候选 → skip（不播，但已扣次）
  8. 有候选 → DeepSeek 从列表选恰好 1 个写口播；prompt 要求权衡 **优质（看名称）** 与 **近且可见**
  9. 返回文案 + 选中 POI
→ App 用火山 ExternalTextToSpeech 在通话中播报
→ 记下当天已讲 + 「最近主动讲解 POI」上下文（供后续追问/足迹）
```

**候选类型**：主动讲解黄点仓 = 风景名胜 + 自然地名（山/河/湖水库/岛/海湾）+ 桥/隧 + 乡镇。**不含村庄** —— 库里 28 万个 `place=village`，自动播报「前方 800 米是张庄村」没有价值；用户主动问「这是什么村」时问路链路仍会返回。  
2026-08-24 起主动讲解与问路共用同一套 PostGIS 撞库（此前主动讲解走高德、完全不查本地库）。  
**半径**：与问路共用场景底径配置，但主动讲解**只有场景、没有语意倍率**（用户未提问）。见 §4.4.1。
### 5.5 和问路的关系

| | 问路 | 主动讲解 |
|--|------|----------|
| 触发 | 用户说话 | 20km + 10min（再加开口冷却） |
| 语音通道 | 火山智能体主对话 | 通话中插入 External TTS |
| 地理 | PostGIS：专名搜索 / 最近 8 条（类型更广，含村庄） | PostGIS：最近 40 条候选（不含村庄）+ 行政区上下文 |
| 扣次 | AI 说完扣 1 次 | 每次检查扣 1 次 |
| 足迹 | 问答后可写 | 本身不写；用户接着问才可能写 |

### 5.6 雷达主地图上的 Dev 标注（仅 `__DEV__`）

通话开启且主动讲解打开时，主雷达地图会叠一层**开发用**标注（正式用户看不到）。实现：`RadarMap` + `lib/proactiveMapDev.ts`；首页有一句图例文案。

| 视觉 | 含义 |
|------|------|
| **黄点** | 附近可能被主动讲解的**候选风景名胜** |
| **蓝点**（浅蓝） | **查询锚点**——用来算「相对上次查询走了多远」的基准位置 |
| **蓝圈** | 位移门槛半径（默认约 20 km，跟高级设置里的位移门槛一致）；走出圈才更可能再去查景点 |
| **紫点** | 当前判定的「前方」POI（`forward_hit`） |
| **绿点** | 上次结果：已开口播报 |
| **灰点** | 上次结果：跳过（未播） |

另外：地图系统自带的**定位蓝点 / 朝向箭头**是用户自己的 GPS，和上表 Dev 标注不是同一套。

## 6. 位置、PostGIS 与地理数据来源（概念澄清）

> **2026-08-24 起高德已完全下线。** POI 撞库全部走自建 PostGIS；逆地理（行政区 / 道路 / 场景）走天地图，失败自动回落本地。

### 6.1 App 上报什么

真机循环上报的是 **经纬度**（通常还有 **朝向 heading**），例如 `(30.65, 104.06)`。  
这只是地球上的一个点，**本身没有地名**。地名全部来自我们自己的 PostGIS 库。

### 6.2 两张表分别干什么

| | `geo_landmarks_cache` | `geo_admin_areas` |
|--|----------------------|-------------------|
| 存什么 | 地物：山河湖桥景点城镇 | 行政区边界：省/地级市/县/乡镇 |
| 几何 | 点 + **线**（河流）+ **面**（湖泊、保护区） | 面 |
| 回答什么问题 | 「半径 N 米内有哪些地标」 | 「我在哪个省哪个市」 |
| 关键查询 | `nearby_geo_landmarks` / `fuzzy_geo_landmarks` | `resolve_geo_context` |
| 规模 | 约 51 万条 | 约 2.3 万个 |

**为什么河流要存 LineString 而不是中心点**：OSM 把一条江切成几十上百个 way，取中心点算距离会差好几公里。存成线之后 `ST_DWithin` 算的是「你到河岸的垂直距离」，「左边这条河」才报得准。返回的经纬度取 `ST_ClosestPoint`，即地物上离你最近的那个点。

### 6.3 `geo_landmarks_cache` 存什么

- **位置** `geom`：geography(Geometry) —— 点/线/面都收  
- **名称 / 类型**：`landmark_type` 六档（town/river/scenery/bridge/mountain/other）  
- **可见半径** `search_radius_m`：按地物大小给。6600 米的冈仁波齐给 80km，村庄给 3km。  
  `nearby_geo_landmarks` 里是 `least(查询半径, search_radius_m)`，**这个字段给小了远处的雪山就永远撞不上**。  
- **讲解文案** `ai_formatted_story`：问答沉淀，撞库命中时可复用（OSM 底库为空）  
- **来源** `source`：`osm` 底库 / `llm_search` / `user_session`  
- **`external_ref`**：如 `osm/way/26303815`，重导时幂等覆盖  

### 6.4 数据从哪来、怎么扩充

**底库**：OSM 全国一次性导入（2026-08-24，`china-260823.osm.pbf`）。流程与脚本：

```
osmium tags-filter   # 按标签筛出讲解相关地物
  → osmium export    # 转 GeoJSONSeq
  → scripts/osm-to-landmarks.py   # 分类 + 定可见半径 + 同名网格去重 → CSV
  → \copy 进 staging → ST_GeomFromGeoJSON → geo_landmarks_cache
```

行政区同理，脚本是 `scripts/osm-to-admin.py`。两个脚本都按 `external_ref` 幂等，OSM 更新后重跑即可。

**沉淀**：`record_geo_landmark_signal` 累积 ask/favorite 信号，够门槛升格进共享缓存。目前只有收藏足迹会触发。

### 6.5 和两条业务线的关系

**问路 FC `get_nearby_landmarks`：**

```
上报 (lat, lng [, heading])
  → resolve_geo_context：行政区 + 城/镇/野场景 → 定半径
  → 用户点名问某地物？
      是 → fuzzy_geo_landmarks 在整个半径内按名字找
            名字对不上 → 近音规则挑真身（ASR 听错救援）
      否 → nearby_geo_landmarks 取最近 8 条
  → 列表（名、距离、左前方/右前方…）回给火山模型
```

专名查询**不是**「取最近 8 条再按名字过滤」—— 用户问的澜沧江可能排在几十条之后。

**主动讲解：**

```
上报坐标
  → resolve_geo_context：行政区（喂 prompt）+ 场景（定半径）
  → nearby_geo_landmarks 取 40 条候选（跳过村庄）
  → LLM 从候选里挑一个写稿
```

### 6.6 场景判定用什么信号

直觉上「落在街道里=城区，落在镇里=乡镇，什么都不落=野外」很合理，实测不行：OSM 的乡镇级边界（L8）只覆盖 **65.7%** 的点，且缺得没规律 —— 可可西里无人区有「索加乡」，康定城区反而没有街道。而且行政区名也骗人：折多山垭口在「榆林街道」辖内，但那是海拔 4200 米的山口。

现在用天地图的 **`poi_distance`**（离最近兴趣点多远），这是直接的人烟密度度量：

| 位置 | poi_distance | 判定 |
|------|-------------|------|
| 成都天府广场 | 1m | urban |
| 康定城区 | 124m | urban |
| 昌都城区 | 242m | urban |
| 然乌湖 | 702m | town |
| 折多山垭口 | 1147m | wild |
| 可可西里 | 1941m | wild |

规则：`≤300m → urban`，`≤1000m → town`，其余 `wild`；再加一条兜底 —— `road_distance > 3000m` 强制 wild（可可西里离 G109 有 48.8 公里）。

天地图不可用时回落本地 `place` 点距离（3km 内有 city → urban，1.5km 内有 town / 1km 内有 village → town，否则 wild）。

> 已知缺口：西藏、福建、海南的省级边界在 OSM 里组装不出来（争议边界导致环不闭合）。天地图正好补上这块 —— 然乌湖现在能拿到「西藏自治区昌都市八宿县然乌镇」。天地图挂了才会退回到只有 L5「昌都市」。

## 7. 外部地理 API 调用一览

只剩**天地图逆地理**一个，每轮主动讲解 / 问路各 1 次。

| 场景 | 接口 | 次数 | 实测耗时 |
|------|------|------|----------|
| 主动讲解 | 天地图 `geocoder` | 1 | 50～170ms |
| 问路 FC | 天地图 `geocoder` | 1 | 同上 |
| POI 撞库（两条链路） | 本地 PostGIS | 0 次外网 | 3～80ms |

**为什么 POI 不用天地图**：实测同一位置（康定城区）天地图周边检索只返回 1 条「靓点坊」美容店，本地库有 12 条（跑马山 96m、折多河 239m、安觉寺 300m…）；专名搜「折多山」它给的第一条在 30 公里外的塔公镇。它的 POI 库不适合导游场景。

**降级**：天地图超时（1.2s）或失败自动回落本地 `resolve_geo_context`，只损失道路名和部分街道名，不阻塞任何流程。两个来源是**并行**发起的，所以本地结果始终就绪。

**Key 必须是服务端类型**。浏览器端 key 从机房 IP 调会 403（`code 301012`），即便带上 Referer —— 本地开发机能通不代表线上能通，这个坑踩过。环境变量 `TIANDITU_KEY`。

历史：2026-08-24 之前问路与主动讲解都打高德 `/v3/place/around` + `/v3/geocode/regeo`，上限 50km、按次计费。下线顺带解决了两个老问题 —— 高德要 GCJ-02 坐标而我们一直送 WGS84（境内偏移 300～500 米），以及 50km 的半径天花板答不了「前面那座雪山」。天地图用 CGCS2000，与 WGS84 实用等价（差异 < 1m），没有这个坑。

客户端从来没有直连过任何地图 API，`RadarMap` 用的是 `react-native-maps`（iOS 苹果图 / Android 谷歌图），只画自己的标记。

**客户端风景库（内存、整库替换）**：`lib/scenicAroundCache.ts`  
- 记住上次搜索中心 + 半径 + 结果；距中心 ≤ **半径 × 50%** 直接读库  
- 出圈或改半径 → 再搜，**用新结果整份替换**旧库（不追加）  
- 黄点预览与正式主动讲解读同一份源数据  

开发预览入口：「我的 → 主动讲解地图」。雷达 Dev 黄点勿做成跟 GPS 心跳狂刷（已由上表库约束）。

## 8. 配额与账号（摘要）

- 计费单位：**问路次数**（主动讲解的「检查」也消耗同一种次数）。  
- 登录用户 / 游客（设备）两套身份；App「我的」展示剩余次数。  
- RTC：进房前拦截用尽；扣次以服务端 `answerFinish` / `proactive` 为准，不以客户端自报为准。

### TODO（暂不做）· 计费演进

当前按「次数」扣费偏粗：短问短答与长聊同价，也和火山实际成本（token / TTS 时长等）不对齐。

**更合理的方向（待调研与产品定案）：**

1. 以**对话 token（及必要时的语音相关用量）**为计费/限额依据，而不是单纯 `answerFinish` 次数。  
2. **优先**：火山侧能否按路鸽体系内的**每个用户（或每个 RTC userId / 业务 user）**独立统计用量，路鸽后端再**拉取用量**做套餐、告警、对账。  
3. 若火山暂不支持按我方用户维度出账：再评估自建估算（回调里的 token 字段、自建计量）等次优方案。  

在未落地前，仍维持本文 §4.3 / §5 的「按次」规则与 RoundID 去重；改计费模型时需同步改后端、App 展示与本节。

成本结构与「把哪一段从火山挪走」见 **§9**（与「用户怎么扣次」是两件事）。

## 9. 成本与省钱（火山 AI 音视频）

> **状态**：方案清单，供产品选型；**尚未定案、未排期实现**。  
> 单价参考：[AI 音视频互动方案计费](https://www.volcengine.com/docs/6348/2123214)（约 **¥12 / 百万 Tokens**，资源包/折扣另算）。  
> 能力拆解与接入方式调研底稿：`docs/ops/volcengine-ai-av-research.md`；官方可替入口：[配置 ASR/LLM/TTS](https://www.volcengine.com/docs/6348/1310542) · [自定义 ASR/TTS](https://www.volcengine.com/docs/6348/1558157) · [第三方大模型/Agent](https://www.volcengine.com/docs/6348/1558158)。

### 9.1 产品目标（2026-07-29 路测后）

| 项 | 约定 |
|----|------|
| 参照用量 | 普通用户一天约 **4 小时**行驶、通话式导游开着（与当日路测同量级） |
| 用户愿付 | **≤ ¥20 / 天**「随便用」，但须有**滥用上限**（时长 / Token / 口播分钟等，待定） |
| 含义 | ¥20 是**零售可接受上限**，不是成本可以等于 20；毛利健康通常要求 COGS 明显低于零售 |

### 9.2 路测账单拆解（为何「换便宜 LLM」几乎没用）

当日约 **250 万互动 Token**，八折后约 **¥25**（原价约 ¥30）。分项大致：

| 账单项 | Token（约） | 占比 | 产品含义 |
|--------|-------------|------|----------|
| **Agent 音频处理** | 142 万 | ~57% | 智能体挂着时的听/VAD/音频管线（「耳朵一直开着」） |
| **TTS** | 80 万 | ~32% | 嘴在说（含问答 + **External TTS 主动讲解**） |
| **音频通话** | 25 万 | ~10% | RTC 管道 |
| **LLM** | 1 万 | ~0.4% | 生成回复文本——**几乎可忽略** |

结论：钱主要在 **长开 Agent + 多说话**；主动讲解文案走 DeepSeek、RTC 对话走豆包，对这笔火山账单影响都很小。

### 9.3 省钱杠杆总览（先产品，再替换）

按「预期省钱量 × 工程代价」粗排。**预期省钱为相对今日形态的量级直觉，不是承诺数字**；替换方案落地前须向火山确认：切出自建后该段是否仍计入「互动 Token」，还是改按各子产品/第三方独立账单。

#### A. 不换栈：产品与会话形态（优先）

| ID | 方案 | 砍哪一块 | 体验代价 | 工程量 |
|----|------|----------|----------|--------|
| **A1** | **按需启停智能体**：默认只挂 GPS/主动讲解；用户按麦或说唤醒词才 `StartVoiceChat`，闲置 N 分钟 `Stop` | Agent 音频（大头） | 不再「全程像打电话随时插话」；唤醒有延迟 | 中 |
| **A2** | **双模式**：导游模式（可全开）/ 省钱模式（推说 + 稀主动讲） | Agent + TTS | 要用户理解套餐或开关 | 中 |
| **A3** | **更稀、更短的主动讲解**（门槛 / 口播短档 / 日封顶分钟） | TTS | 路上更安静 | 低（设置已有一部分） |
| **A4** | **主动讲解不走火山 External TTS**：文案仍 DeepSeek，音频走 HTTP TTS / 端侧播放 | 火山 TTS | 与 RTC 抢麦、音质/打断体验要重做 | 中 |
| **A5** | 判停/VAD/降噪调参，减少车噪误触发 ASR 轮次 | Agent 音频（次要） | 可能漏听短指令 | 低～中 |
| **A6** | 商业：资源包、代理折扣（八折→2/3 折） | 整单乘数 | 无 | 商务 |

**建议默认先压 A1 + A3 + A6**：不动架构也能把「4 小时耳朵常开」打掉一大截。

#### B. 火山仍进房，但换成「自定义/第三方」组件

火山方案支持在 `StartVoiceChat` 里换 ASR / LLM / TTS，或走 CustomLLM / 自定义 ASR·TTS 协议（见上官方链接）。路鸽已有 HTTP TTS、DeepSeek 边车，可部分复用。

| ID | 方案 | 砍/挪哪一块 | 注意 | 工程量 |
|----|------|-------------|------|--------|
| **B1** | **CustomLLM / 第三方 LLM**（DeepSeek、更小豆包、自建） | 账单里的 LLM 段 | 今日 LLM 仅 ~0.4%，**对总成本几乎无感**；价值在效果/延迟/统一人设，不是省钱 | 中 |
| **B2** | **自定义 / 更便宜 ASR**（其他云 ASR，或自部署经网关） | Agent 音频相关 | **最大技术杠杆之一**；须确认计费是否真正离开「互动 Token」；车噪与打断质量要重验 | 高 |
| **B3** | **自定义 / 更便宜 TTS**（火山 HTTP TTS 按字符、其他厂商、端侧） | TTS | 与 A4 类似；流式首包延迟与音色一致性是坑 | 中～高 |
| **B4** | **暂停/恢复 AI 播报**、减少无效播报轮 | TTS + 少量 Agent | 官方有「暂停或恢复 AI 播报」能力，偏产品编排 | 低～中 |
| **B5** | **端到端实时语音大模型**（官方可选路径） | 可能合并 ASR+LLM+TTS | **未必更便宜**，先当能力选项，不当省钱默认 | 高 |

#### C. 大幅自建（几乎退出「一站式互动 Token」）

| ID | 方案 | 含义 | 风险 |
|----|------|------|------|
| **C1** | 保留 RTC 只做传输，ASR/LLM/TTS 全自建流水线 | 计费回到各云按量 + 自研延迟/打断 | 工程最大；易回到旧 HTTP 语音的体验坑 |
| **C2** | 退回「非 RTC」主路径（端侧/HTTP ASR + DeepSeek + HTTP TTS） | 成本可控、已有部分代码 | **全双工打断、车载延迟**可能明显变差；与当前真机产品形态冲突 |
| **C3** | 仅「主动讲解」自建播放，「问路」仍走火山 | 混合：闲时便宜、问答仍贵 | 状态机复杂（两套嘴、抢麦） |

### 9.4 与用户定价的对齐（零售 ≤ ¥20/天）

仅砍 COGS 不够，套餐要防止「挂机刷耳朵」：

1. **日封顶**：例如每日 RTC 智能体在线时长、或估算 Token、或口播分钟，触顶降级为「只主动讲 / 只文字」或停麦。  
2. **计费演进**（§8 TODO）：长期应用量对齐成本；短期可用「次数 + 日时长帽」。  
3. **套餐设计**：¥20 对应「正常自驾日」而非无限挂机；滥用帽要在文案里写清。

### 9.5 选型时建议问清的问题（对火山 / 对自己）

1. 账单里「Agent 音频处理」是否≈智能体在线时长线性？停 `VoiceChat` 但不断 RTC 房间，是否还计这段？  
2. 自定义 ASR/TTS / CustomLLM 后，该段是否**退出** ¥12/百万互动 Token，改按子产品价？  
3. External TTS 与对话 TTS 是否同一单价、同一桶？  
4. 资源包与代理折扣后，4 小时「全开」COGS 能否进 **¥8～12**（才撑得起零售 ¥20）？

### 9.6 暂不执行

在你圈定优先方案（例如 A1+A3 或 B2）之前，**不改**线上 `voiceChatConfig` / 启停策略。选定后另开实现任务，并回写本节「已定案」行。

## 11. 已知产品约定 / 后续改动时注意

1. **主动讲解检查即扣次**：即使用户听不到播报（无候选、开口冷却），检查请求已计费。若产品要改成「只有播报才扣」，需同时改后端与本文 §5。  
2. **风景名胜 only**：主动讲解候选不要再塞回河流/地名等，除非产品明确放开并改本文 §5.4。  
3. **当天去重**：键为规范化名称 + 可选 POI id；换设备不会共享，除非以后改为服务端去重。字段名仍叫 `amap_poi_id`（客户端 6 个文件在用），实际存的已是缓存行 UUID，属遗留命名。  
4. **改门槛 / 口播长短 / 搜索半径**：用 App「我的 → 高级设置」，不要再靠环境变量路测。  
5. **改扣次时机**：RTC 问路以 `answerFinish` 为准；不要改回客户端随意上报。  
6. **地理数据只有本地库**：不要再引入外部地图 API。要扩充数据就走 `scripts/osm-to-*.py` 重导，或让沉淀机制升格。改地理策略时同步更新 §6。
7. **高级设置面向路测**：正式上架前可再收口哪些项对普通用户可见。
8. **主动讲解与对话连贯（2026-07-29）：** 产品要求追问能接上刚讲的点。火山 FAQ：**External 自定义播报文本会放入历史对话**（[1449206 Q2](https://docs.volcengine.com/docs/6348/1449206?lang=zh)）。实现上：播完后发 **`ExternalPromptsForLLM` 话题锚定** + system 指代规则 + HistoryLength=16；细节见 `TODO.md` **F0/F1**。
